01 / Executive summary

What the project solves

Audience-analysis requests arrive through a Monday.com CRM board. Traditionally, an analyst interprets the ticket, searches prior work for relevant logic, writes and executes SQL in Databricks, prepares the result, and returns it for audit. The automation connects these steps and uses an LLM to assist with repeatable work while keeping an auditor in the approval path.

Before

Request details, code examples, and past decisions are spread across historical tickets and analyst folders. Analysts repeatedly interpret requirements and reconstruct familiar query logic.

Intervention

Use the ticket as the trigger and source of request context; use Cursor's LLM and historical references to support interpretation and SQL work; use Databricks to retrieve results; return them to the ticket.

After

A connected, partially automated workflow prepares results for auditor review. Stakeholder communication remains gated by human validation.

Positioning: This is an AI-assisted workflow automation with human oversight—not a claim of fully autonomous analytics or a model trained from scratch.

04 / Historical knowledge strategy

How two years of manual work can help the LLM

The folder of prior tickets, code, and request information represents accumulated operational knowledge. It can help an LLM recognize repeated request patterns, but its usefulness depends on how the context is selected and checked.

Reference material

  • Previous request tickets and their wording
  • Code or SQL associated with completed requests
  • Basic request information and supporting notes
  • Known filters, definitions, or query patterns where documented

Recommended use pattern

  • Find examples relevant to the current request rather than blindly reusing all history
  • Check whether table names, fields, definitions, and date logic remain valid
  • Prefer current, approved logic when historical examples conflict
  • Keep the generated query and assumptions visible to the reviewer
Terminology: If the LLM receives files or snippets as prompt/context, call it reference-based context engineering. If a search layer retrieves relevant examples at runtime, it may be described as retrieval-augmented generation (RAG). Fine-tuning is a separate process that updates model weights.

07 / Quality and governance

Keep a human accountable for the final answer

Workflow controls described

  • Output is returned to the originating Monday.com ticket.
  • An auditor checks the output before stakeholder delivery.
  • Historical code and tickets are reference material, not assumed ground truth.

Controls to confirm or implement

  • Least-privilege access to Databricks and MCP tools
  • SQL allow-listing or other execution safety checks
  • Query timeouts, bounded retries, and clear failure statuses
  • Validation for date ranges, filters, result grain, and row counts
  • Audit trail for request ID, query version, result status, and reviewer outcome
  • Redaction of sensitive fields from logs and prompts where required
Security principle: An LLM-generated query should never receive broader permissions than the human or service account requires. Do not put credentials, secrets, or sensitive customer-level data into portfolio materials.

09 / Improvement roadmap

How the workflow can mature

Phase 1

Instrument

  • Log timestamps at each stage
  • Separate machine duration from human effort
  • Capture auditor acceptance and correction reasons
Phase 2

Harden

  • Validate SQL and data scope
  • Make retries bounded and observable
  • Use current approved logic and clarify ambiguous requests
Phase 3

Optimize

  • Group requests by complexity and repeatability
  • Improve retrieval of relevant historical examples
  • Scale only where quality and efficiency are demonstrated
